第Ⅶ部 実践　─　2

MIDI・MPE・MTS-ESP・MIDI 2.0 ── 音高を届ける層

直感レイヤー

音源ひとつを微分音で鳴らすだけなら、前節（Ⅶ-1）の .tun や .scl/.kbm をロードすれば済みます。本当の課題はその先、複数の音源・DAW・ハードへ、微分音を「通信し、共有する」ことです。
旧来の MIDI は「1オクターブ12音」を前提に設計されているため、演奏情報そのものにピッチ情報を載せる標準的な手段がありません。この壁を越えるために積み重ねられてきた後発の仕組みがピッチベンドの多チャンネル運用（MPE）、プラグインを一斉にリチューンする MTS-ESP とハブ型ツール、そしてプロトコルそのものを刷新する MIDI 2.0を、静的な「ロード」と動的な「通信」という軸で整理します。

MPE ── 和音で別のベンドを与える定番

MPE は、和音の各音を別々の MIDI チャンネルに配り、チャンネルごとに独立したピッチベンドをかける仕組みです。これにより「和音の中で音ごとに違う微調整」〝31edo などの各音を正確な位置へ寄せること〟が可能になります。
ROLI Seaboard や LinnStrument などの表現力の高いコントローラの規格として広まり、多くのシンセ（Serum 2、Vital、Pigments、u-he 系など）が対応します。31edo の演奏ではプラグイン／DAWで各音を最寄り12音＋ベンドに分解し、MPE 対応音源がそれを正しい音高で発音します。
制限は同時発音数：MPE は1音1chなので、15ch 運用なら和音は最大15音。31edo の分厚いクラスタには足りることが多いものの、上限がある点は意識します。

本書後半で扱う「白鍵3段・黒鍵2段のチャンネル鍵盤」Ⅶ-5）は、MPE とは別の発想で、ピッチクラスを固定的に3チャンネルへ振り分ける方式です。MPE が「音の発音ごとに動的に ch を割る」のに対し、こちらは「どの音名はどの ch」と静的に決める。Reaper のようにチャンネル別に色分け表示できる環境では、この静的割り当てが譜面の可読性を生みます。

MTS-ESP とハブ型ツール ── リチューンを一括配信する

MTS-ESP（ODDSound 社）は、近年の微分音制作を大きく変えた仕組みです。DAW に MTS-ESP Master を挿し、そこに .scl や音律を読み込むと、MTS-ESP 対応の全プラグイン（Client）が自動的にその音律にリチューンされます。ピッチベンドを一切使わないため、MPE の同時発音制限も、ベンドレンジの管理も要りません。普通の12鍵 MIDI をそのまま弾いても、音源側が31edo で鳴る。対応音源は増え続けており、無料のものでは Surge XT や Dexed、有料では Pigments・FabFilter Twin 3・u-he 各種・TAL 各種・Serum 2 などが Client 対応です（対応状況は Xenharmonic wiki の対応プラグイン一覧が随時更新しています）。「まず MTS-ESP、足りなければ MPE」が現在の実務的な優先順位になりつつあります。

注意したいのは、チューニングファイルを読めることと、MTS-ESP に対応していることは別だという点です。たとえば Vital は .scl/.kbm/.tun のインポートに対応する一方、MTS-ESP Client ではありません。前者は静的ロード（曲の前に固定音律を読ませる）、後者は動的通信（Master から一括で、演奏中でも配信する）で、層が違います。音源を選ぶときは「どちらの方法で微分音化できるのか」を確認するのが確実です。

同じ「リチューンを一括管理する司令塔」として、Entonal Studio（Node Audio）も有力です。これは 任意の AU/VST2/VST3 音源をホストして微分音化するプラグインホストで、内部の音源を MTS-ESP かMPE、ピッチベンドのいずれかでリチューンします。radial graph（放射状グラフ）で音律を直感的に編集でき、スケールは Scala 形式で入出力可能です。MTS-ESP が「対応音源だけを裏で一括調律する規格」であるのに対し、Entonal Studio は「非対応音源も抱え込んで微分音化する容れ物」であり、MTS-ESP に対応していない好みのシンセを微分音で鳴らしたいときのより現実的な受け皿になります。

MIDI 2.0 ── 期待と、肩透かし

MIDI 2.0（2020年正式化）は、ノートに高分解能の音高を1音ずつ載せられるようにしました。中核は二つです。
ひとつは Pitch 7.9——
Note On/Off に付ける属性で、上位7ビットが従来のノート番号、下位9ビットが半音の512分割（約 0.195¢ 刻み）を表します。
もうひとつは Per-Note Pitch Bend——
従来チャンネル全体にかかっていたベンドを、32ビット分解能で特定のノートだけに適用できます。MPE のようにチャンネルを使い切る必要も、15音の制限もありません。原理的には、ベンドやチャンネル分割という「回避策」そのものが要らなくなります。

ところが、2026年現在も微分音コミュニティの受け止めは手放しの歓迎ではありません。理由は、この仕組みが音高を1音ずつ逐一送る設計だからです。演奏中に音律そのものが動く音楽にはこれは強力です。
しかし実際に作られる微分音曲の大半は音律が固定で、その用途には「毎ノートに音高を明示し続ける」のは冗長すぎます。欲しいのは各音への逐一指定ではなく、「この曲は 31edo」などと一度宣言して音律を共有する仕組みなのです。
ところが 2.0 の華々しい部分（Pitch 7.9 と Per-Note Pitch Bend）は、まさにそこを直接には埋めませんでした。
また、微分音の楽曲を制作するにあたり、音域はそのまま12音よりも多くの音を扱えるようになればよかったものの、MIDI の鍵盤の情報（Note No.）は従来通り、一つのチャンネルにつき0から127までしかなく、そもそも音の多い音律を配置すると音域が狭くなってしまう問題は解消されておらず、残念ながら実際に微分音コミュニティ内では「肩透かしを食らった」という空気が流れているのも現状です。

そこで切実に待たれているのが、MIDI 2.0 のもう一本の柱 MIDI-CI（MIDI Capability Inquiry）側の整備です。
MIDI-CI は接続した機器どうしが「何ができるか」を交渉して設定を自動化する枠組みで、なかでも Profile Configuration が鍵を握ります。プロファイルとは「この楽器（チャンネル）はこう振る舞う」という共通の型のことで、もし微分音プロファイル（たとえば "Microtonal Tuning Profile" のようなもの）が規格として定義されれば、コントローラが要求するだけで音源側がチャンネル配分やチューニングを受け取る準備を整えられます。加えて Property Exchange（JSON でデバイス情報をやり取りする仕組み）を使えば、音律を人間にも読める形式で一括送受信・確認できる。従来 MTS の SysEx のように音源依存だったものが、オフィシャルでエラーに強い形に置き換わります。コミュニティが「Profile Configuration を整備してほしい」と求めているのは、この音律共有の標準化です。

現状はまだ発展途上です。仕様上の柱は揃いつつあるものの、微分音プロファイルというものはまだ策定されておらず、実装側にも不具合報告があります。たとえば Pitch 7.9 の解釈が送受信側でずれ、出音が一瞬 12edo で鳴ってから正しい微分音ピッチへ「ヒョイッ」と動く現象や、メッセージ量が膨らむ複雑な曲でのタイミングのずれなども報告されています。「将来の本命」であること自体は変わりませんが、現場の主力は当面 MTS-ESP と MPE、というのが正直な現在地です。

MIDI 2.0 仕様の一次情報は MIDI Association の MIDI 2.0 ページにまとまっています。日本語サイトでは AMEI が同じ仕様書群を配布していますが、内容は英語です。

精密レイヤー ── 分解能の対比と、チャンネル運用

各方式の音高分解能を並べます。MIDI 1.0 ピッチベンドは14ビット（0〜16383、中央8192）で、既定のベンドレンジ±2半音なら約 0.024¢ほどであり、31edo の 38.7¢ を送るには十分です。実務では当然ピッチベンドは専らピッチベンドのために用いるため、そもそも使いません。もし使ったとしてもベンドレンジを Master と一致させていないと、全体が音痴になります。MTS-ESP がベンドを使わないのは、この「レンジ整合の事故」を根絶するためでもあります。MIDI 2.0 の Pitch 7.9 はさらに粗く、7ビットで半音単位でMIDI上にある128から最寄りのピッチを選び、残りの9bitで半音の512分割＝約 0.195¢/stepをしていするものであり、先ほどのベンド値より精度は粗くなります。

0.195¢ は「もうひと声」かもしれません。.scl はセント値を小数で好きな桁数だけ書けるため、実質的な分解能はテキストの精度そのものであり、〝C4＝261.6255653 Hz〟のような値も、.sclや.tunv2 なら丸めずに書けます。Pitch 7.9 は量子化された固定格子なので、純正比を厳密に積み上げたいときや、微小なコンマの差を正確に扱いたいときには、静的ロード（.tun／.scl）のほうがなお有利な場面が残ります。「演奏中に動かせる分解能」と「固定だが任意精度」は、まだ完全には両立していません。

チャンネル運用の上限も明示します。MIDI 1.0 は16ch。MPE は1chをグローバル制御に使うため実質15ch＝15音同時。本書のチャンネル鍵盤方式（Ⅶ-5）は31音をピッチクラスで3chに畳むため、和音の同時発音は ch あたりの制限を受けず、かつ Ch.4 を制御に残せます。静的割り当てゆえの効率です。方式ごとに「何がボトルネックか」（同時発音数か、レンジ整合か、規格の成熟度か、分解能か）が違う点を理解して選ぶのが要点です。

この節の要点 動的通信はMPE（1音1ch＋独立ベンド、〜15音）、MTS-ESP（対応 Client を一括リチューン）、MIDI 2.0（Pitch 7.9で1音ずつ高分解能指定）。
チューニングファイル対応と MTS-ESP 対応は別物で、Vital は前者のみでMTS-ESP 非対応。
Entonal Studio は任意音源をホストして MTS-ESP／ベンドで微分音化するハブ。
MIDI 2.0 は1音ずつ送る設計ゆえ音律固定曲には過剰で、コミュニティはProfile Configuration による音律共有の標準化を待望している。
Pitch 7.9 約0.195¢/step で精密さに欠け、任意精度で書ける .scl がなお有利な場面も残る。
